# M06/E09/v001 — где FM теряет качество политики при меньшей PEHE?

**Статус:** диагностический post-hoc протокол после просмотра [M06/E08](../../results/E08/v001/20261020T120435_272674Z/README.md). Это не новое независимое подтверждение и не подбор метода по eval. Протокол и код фиксируются до детального анализа сохранённых score. Новый CausalPFN-инференс и обучение baseline не нужны.

## Вопрос и альтернативные объяснения

В `threshold_gate` E08 при K128 FM немного точнее global CV по средней normalized PEHE (`0,9454` против `0,9614`), но хуже по oracle regret@10% (`0,3875` против `0,2049`). Возможное объяснение: FM лучше на большинстве eval-строк, но хуже оценивает **истинную верхнюю дециль** CATE, от которой зависит таргетинг. Альтернатива: ошибка верхней дециль у FM не выше; проигрыш возникает из-за ошибок порядка около порога выбора, шума ранжирования или калибровки score. Эти механизмы не эквивалентны и из одного PEHE не следуют.

## Данные и точный анализ

- Только 8 `smooth_gate` и 8 `threshold_gate` случаев E08, seeds `3101–3108`, те же `512` eval-строк, без замен. Источник — сохранённые `base.npz` (истинный `tau_eval`), `score_fm_K64.npy`, `score_fm_K128.npy`, `score_global_cv.npy`, `score_adjusted_K128.npy`. Проверить SHA каждого файла по неизменяемому `local_files.csv` E08 и manifest самого снимка; остановиться при несовпадении.
- Для каждого случая выделить **oracle top-10%**: `ceil(0.1×512)=52` строк с наибольшим `tau_eval`, stable sort по исходному индексу при равенстве. На этих 52 и остальных 460 строках считать среднюю квадратную ошибку FM K128 и global CV. По всем 512 повторно сверить PEHE и regret@10% с `all_metrics.csv` E08. Использовать **сырую** шкалу CATE внутри семьи; разные семьи не объединять.
- **Основной диагностический контраст:** `MSE(FM_K128)−MSE(global_cv)` на oracle top-10% отдельно в каждой семье. Предзаданный описательный ориентир предлагаемого объяснения в `threshold_gate`: средний контраст `>0`, положителен минимум в `6/8` генерациях, а средний контраст на остальных 460 строках `<0`. Если любое условие не выполнено, остановить именно объяснение «FM ошибается сильнее на верхней дециле»; не подменять его вторичной метрикой.
- Дополнительно для каждого score (`FM K64/K128`, `global CV`, `adjusted K128`) считать средний истинный CATE среди выбранных score top-52, oracle regret, долю пересечения с oracle top-52 и корреляцию Спирмена score с истинным CATE. Это разложит потерю политики на общую точность и фактический выбор; результаты являются диагностикой уже просмотренных данных.
- Для среднего основного контраста отдельно по каждой семье дать 5000 bootstrap-перевыборок **seed-случаев** с seed `2909`, percentile 95% интервал. Пары smooth/threshold используют общие covariates/treatment/noise при одинаковом seed; не считать 16 случаев независимыми популяциями. Интервал описывает фиксированный синтетический генератор, а не внешнюю кампанию.

## Исполнение и решение

Runner `tools/run_m06_e09.py`: `--help`, `--check` (наличие/хеши и форма, без метрик), `all`, `--status`; TTY-прогрессбар показывает проверку/анализ/упаковку, число из 16 случаев, elapsed/ETA. Не-TTY выводит короткие стадии. Оценка: CPU, <5 секунд анализа после чтения файлов, RAM <100 MB, новый локальный диск <1 MB; основание — 16 массивов по 512 score и 16 небольших `base.npz`. Код и этот протокол коммитить до `all`.

Команды из корня: `.venv/bin/python tools/run_m06_e09.py --check`, `.venv/bin/python -u tools/run_m06_e09.py all`, `.venv/bin/python tools/run_m06_e09.py --status`. Компактный результат — новый неизменяемый `results/E09/v001/<run-id>/` с парными диагностическими таблицами, сводкой, исходным commit/SHA кода и индексом SHA использованных локальных файлов. Исходные score остаются в `artifacts/local/m06_e08_results/` без изменений. После результата обновить README/roadmap и валидатор; даже выполненный ориентир не доказывает причинный механизм и не создаёт новый selector.
