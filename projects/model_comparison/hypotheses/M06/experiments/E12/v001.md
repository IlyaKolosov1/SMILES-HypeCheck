# M06/E12/v001 — есть ли запас для адаптивного размера контекста?

**Статус:** ретроспективная проверка возможности метода на уже просмотренных score; это не независимый тест и не доказательство полезности правила. Код и этот протокол фиксируются до нового пообъектного анализа. FM повторно не запускается.

## Вопрос

Рост K улучшал среднюю PEHE FM в E08 и E11, но неясно, помогает ли большой контекст **каждому** запросу. Если почти всем нужен большой K или oracle-распределение бюджета мало отличается от случайного, разрабатывать query-wise адаптивный K бессмысленно. Если выигрыш сосредоточен, можно позже проверить правило, основанное только на train и доступных до дорогого инференса признаках.

## Источники и вычисление

- Использовать все 16 heterogeneous ячеек `smooth_gate`/`threshold_gate`, seeds `3101–3108`, из завершённого [E08](../../results/E08/v001/20261020T120435_272674Z/README.md): K64/K128, 512 одинаковых eval-строк в каждой ячейке. Два constant-CATE контроля показать отдельно, не включать в gate.
- Использовать все 16 бинарных ячеек `alpha=0.02/0.15`, seeds `5201–5208`, из завершённого [E11](../../results/E11/v001/20261020T144232_220031Z/README.md): K128/K512, 512 одинаковых eval-строк. Эти ячейки уже просмотрены; не считать их независимым подтверждением E08.
- Проверить SHA всех локальных файлов по снимкам, исходный Git SHA, формы и конечность score, истинные `tau_eval`, соответствие сохранённой PEHE. Для запроса `i` вычислить `g_i=(tau_i−score_small_i)^2−(tau_i−score_large_i)^2`: положительное значение значит, что большой K уменьшил squared error. Истина используется **только** для оценки oracle-границы, не предлагается как вход рабочего метода.
- Для каждой ячейки сравнить all-small, all-large, случайное назначение большого K половине запросов (ожидаемый MSE = полусумма двух MSE) и **oracle-top-half** по `g_i`. Последнее — недостижимая верхняя граница при бюджете 50% дорогих запросов. Указать долю `g_i>0`, MSE и PEHE всех вариантов, отношение `MSE_oracle50/MSE_all_large` и улучшение oracle относительно random50. Привести разброс по seed; не объединять разные DGP в единый CI.

## Заранее выбранный gate

Метод с адаптивным K имеет смысл разрабатывать **только если в обеих E08-семьях** средний oracle50 MSE не превышает all-large более чем на 5% **и** превосходит random50 по MSE минимум на 5% относительно all-large. На E11 показать те же числа как чувствительность, не использовать её для изменения gate. Если gate провален, не обучать selector на просмотренных `tau`; оставить постоянный большой K как лучший из двух по средней точности в этих задачах. Даже пройденный gate говорит только о наличии oracle-запаса: следующий эксперимент обязан учить правило на train/validation без истинного eval-CATE и проверять на новой семье.

## Результат и воспроизводимость

`tools/analyze_m06_e12.py --check` проверяет источники без вычисления `g_i`; `run` делает быстрый анализ с progress bar/редким non-TTY статусом. Сохранить компактный неизменяемый снимок `results/E12/v001/<run-id>/`: таблицы по ячейкам, gate, протокол, code Git SHA/SHA, SHA источников и краткий вывод. Локальные пообъектные `g_i` остаются только в `artifacts/local/`. При отсутствии исходника анализ останавливается; заменять seed или ячейку нельзя. Ожидаемое время — минуты или меньше, RAM <1 GB.
