# M06/E06/v001 — объясняет ли размер train остаточный выигрыш FM на ACIC?

**Статус:** протокол зафиксировать до расчёта. Это диагностический факторный тест после [E05](../../results/E05/v001/20261020T094727_834998Z/README.md), где FM выиграла у скорректированного local на IHDP, но не на ACIC. Результаты ACIC уже просмотрены; проверка не считается независимой валидацией статьи.

## Вопрос, данные и план

На **одних и тех же** ACIC covariates, outcomes и 961 eval-строке варьировать два ресурса:

| Фактор | Уровни | Что фиксировано |
| --- | --- | --- |
| Размер train bank `N` | 672 и полный 3841 | Малый bank — однократная равновероятная выборка без возвращения из прежних train-ID, `numpy.default_rng(2026)`, отсортированные ID; выбор не использует outcome/treatment. Никакого нового eval split |
| Контекст `K` | 128 и 224, по половине каждого treatment arm | Один и тот же feature-kNN для FM, direct local и adjusted local; при данном `N` меняется только число соседей |

Все 10 сценариев [ACIC M01/E12](../../../M01/results/E12/v001/20261019T220135_061366Z/README.md); **primary** заранее включает только 8 с неоднородным CATE (`1,4,5,6,7,8,9,10`), сценарии `2,3` с постоянным CATE — sanity check. Малый bank общий по ID для сценариев. Перед расчётом проверено: при таком выборе минимум treated в малом bank — 123; K=224 требует 112/arm. Поэтому исходное предложение K=512 при N=672 **невозможно** (требует 256/arm), а уровни 128/224 выбраны до просмотра новых score. Outcome, covariates и исходный group-safe train/eval split прежние. Истинные `mu_t/CATE` используются только для оценки. Полный N/K512 из E05 остаётся архивной точкой сравнения, не пятой ячейкой primary.

Для каждой ячейки `(N,K)` заново выбрать контекст из соответствующего bank и получить CausalPFN-score прежним checkpoint/revision без калибровки. Внутри каждого `(scenario,N)` один раз обучить **те же** две arm-регрессии с 5-fold cross-fit, как в [E05](../E05/v001.md): `HistGradientBoostingRegressor(learning_rate=.05, max_iter=200, max_leaf_nodes=31, l2_regularization=1.0, random_state=42)`, folds `KFold(shuffle=True, random_state=42+arm)`, обучение только на bank. Для каждого донора `i` обе части коррекции `Y_i + m_t^(-fold(i))(x) − m_t^(-fold(i))(X_i)` вычисляет одна arm-модель без `i`. Тот же fitted nuisance используется при обоих K данного N. Сохранить `adjusted_feature`, `global_cv`, `local_feature` и `train_ate`; score FM и контексты — в `artifacts/local/`.

## Метрика и заранее заданное решение

Для каждого heterogeneous сценария и ячейки `D(N,K) = [PEHE(adjusted_feature) − PEHE(fm_feature)] / SD(true CATE на всех 961 eval)`. Положительный знак — преимущество FM. **Primary:** внутри сценария `Δ_N = [D(672,128)+D(672,224)−D(3841,128)−D(3841,224)]/2`. Это проверяет, растёт ли остаточная польза FM при уменьшении bank, усредняя по заранее заданным K. Показать восемь `Δ_N`, среднее и число положительных. Описательный ориентир для продолжения «малого train»-объяснения: `mean Δ_N > 0.05`, минимум `6/8` положительных и `mean D(672,128) > 0.05`. Если не выполнен, малый train сам по себе не объясняет IHDP-сигнал в этой постановке.

**Вторично:** `Δ_K = mean_N[D(N,128)−D(N,224)]` для каждого сценария; interaction N×K; четыре абсолютных D; PEHE и oracle regret@10% у FM, adjusted, global cross-fit, direct local и train-ATE. Для top 10% использовать `ceil(.1*961)`, stable sort. Эти сравнения не заменяют primary при неудобном результате. Условный интервал среднего `Δ_N` получить 500 парными bootstrap-перевыборками **eval-строк внутри каждого сценария**, одинаковыми индексами для всех четырёх ячеек; фиксировать `SD` исходного eval. Сценарии разделяют covariates, интервал не является междатасетной значимостью.

Даже положительный итог E06 показывает эффект `N` **внутри ACIC при K=128/224**, не доказывает причину результата IHDP: у семей разные DGP, доли treatment, признаки и размер eval. Доступ к меткам различается: adjusted/global используют весь train bank, FM на каждый запрос получает K labels. Никаких новых весов смеси, tuning или выбора порога по eval.

## Проверки, ресурсы и исполнение

Проверить SHA ACIC-источника, исходные train/eval ID, их непересечение по группам, состав малого bank, treatment counts для K224, одинаковый порядок eval и paired context, прежнюю ревизию/хеш checkpoint. Запуск остановить при расхождении. Предварительный локальный замер **без подсчёта PEHE**: для двух запросов CausalPFN после загрузки заняла около 0,03–0,04 с на ячейку, peak RSS около 550 MB. Полный объём — `10 × 2 × 2 × 961 = 38 440` FM query и 200 небольших HistGB fits; оценка 10–25 минут CPU, RAM <2 GB, локальный диск <200 MB. Это экстраполяция, runner показывает фактические elapsed/ETA.

Прогрессбар в TTY — одна строка: stage, scenario, N/K, обработано/всего query, elapsed, ETA; отдельно число готовых fits. При перенаправлении — редкие строки статуса. `status.json` обновляется по стадии и batch; `--status` ничего не считает, `--check` не обучает и не получает FM-score. При прерывании папка `incomplete`; resume в v001 нет, новая попытка получает новый run-id. Протокол и runner коммитятся **до** нового FM-инференса. Полные score/контексты и bootstrap — `artifacts/local/m06_e06_results/<run-id>/`; компактный неизменяемый снимок с протоколом, SHA источников/кода, метриками, парными разностями и ограничениями — `results/E06/v001/<run-id>/`.

Команды из корня: `.venv/bin/python tools/run_m06_e06.py --check` проверяет входы; `.venv/bin/python -u tools/run_m06_e06.py all` выполняет расчёт; `.venv/bin/python tools/run_m06_e06.py --status` показывает прогресс. Анализировать только после полного `RUN COMPLETE` и проверки снимка.
