# M01/E18/v001 — зависит ли native retrieval от состава оцениваемой когорты?

**Статус до запуска:** протокол и код фиксируются до нового FM-инференса и просмотра сравнительных score. Это **механистический разведочный аудит** уже изученного Criteo E17, не новая проверка выигрыша по uplift и не способ пересмотреть отрицательный primary E17.

## Вопрос и дизайн

Встроенный retrieval CausalPFN сортирует слабые CATE-прогнозы всех запросов и даёт группе запросов общий контекст. Поэтому один и тот же человек потенциально получает другой контекст и score при изменении набора соседних запросов. [Описание алгоритма в статье CausalPFN](https://arxiv.org/html/2506.07918v2#D2-Model-Details). Проверяем это непосредственно, удерживая неизменными train bank, веса FM, preprocessing, `K=512`, outcome `visit` и сами eval-строки.

- Источник: завершённый [M01/E17/v001](../../results/E17/v001/20261021T204248_950468Z/README.md), его 51 200 train и 1 300 000 eval строк. Сверить manifest, SHA выбранных локальных массивов, исходные данные, train/eval ID и код до inference. Исходные E17 файлы не изменять.
- Зафиксировать **4096 anchor eval-строк**: отсортированные позиции из `default_rng(20261030).choice(1_300_000, 4096, replace=False)`, без использования outcome или score. Сопоставить сохранённый native score, полученный при оценке всех 1,3 млн, с новым native score **тех же anchors**, если подать только их 4096 как cohort. Повторить установленный алгоритм `iter_native_batches`, включая оба потенциальных treatment-запроса, `max_query_length=4096`, 256 соседей на arm и те же train-only weak-CATE модели.
- Сохранить для каждого anchor абсолютное изменение FM-score, изменение direct-local-score по фактическим native контекстам и долю совпадающих train-контекстов. Контексты сравнивать отдельно для обоих counterfactual queries. Фактический `Y` anchors не участвует в этом аудите.

## Заранее выбранное чтение результата

Основные диагностические величины: доля anchors с изменённым хотя бы одним контекстом, доля с `|Δ CATE-score| ≥ 0,01` (один процентный пункт прогнозируемого эффекта), медиана/90-й перцентиль абсолютной разности и пересечение двух top-10% списков **внутри anchors**. Показать те же score-разности для direct-local и Spearman корреляцию. Описательный сигнал для дальнейшей проверки механизма: изменённый контекст у >10% anchors **и** `|Δscore|≥0,01` у >10% **или** overlap двух anchor top-decile <90%. Порог не является статистическим тестом или доказательством роста истинного uplift.

Если диагностический сигнал отсутствует, остановить эту ветку. Если он есть, следующий эксперимент возможен только с отдельным протоколом на новых данных и `uplift@10%`/Q̂ как первичными метриками: проверить, влияет ли стабильность retrieval на решение о таргетинге. Не переносить вывод о cohort-зависимости score на причинную эффективность политики без такого теста. Различие полного и сокращённого cohorts также меняет адаптивные batch-границы; E18 не отделяет изменение конкретного контекста от возможного взаимодействия query токенов в модели.

## Ресурс, файлы и проверка

За ориентир взять уже измеренный E17 benchmark: 4096 eval / 8192 counterfactual queries native inference за 125,4 с на CPU. Повторная загрузка данных и weak learner добавят время; план **до 30–60 минут** на той же машине, 1–3 ГБ RAM плюс исходный E17 dataset, без нового feature-kNN FM. Runner обязан показывать progress bar по native запросам, stage/processed/total и ETA. `--check` проверяет provenance без FM; `--status` показывает состояние; `all` выполняет один расчёт после коммита кода/протокола.

Полный per-anchor файл и временные массивы — в `artifacts/local/m01_e18_v001_results/<run-id>/`. Неизменяемый компактный снимок — в `results/E18/v001/<run-id>/`: протокол, код, Git SHA и SHA скрипта, хеши источников и выхода, сводная диагностика, статус и краткое ограничение вывода. При ошибке сохранить `incomplete` локально, не подменять заранее выбранные anchors или пороги.
