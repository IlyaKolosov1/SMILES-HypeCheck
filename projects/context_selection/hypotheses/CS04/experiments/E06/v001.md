# CS04 / E06 / v001 — train-only отбор признаков до инференса FM

**Статус до расчёта:** план. Протокол и runner фиксируются в Git до просмотра результатов. Это проверка осуществимости, а не подтверждение метода и не оценка качества CausalPFN.

## Вопрос

[E05](../../results/E05/v001/20261020T165022_718458Z/README.md) показал, что удаление известных из генератора шумовых входов резко снижает CATE RMSE CausalPFN при тех же строках. Можно ли восстановить полезные столбцы **только по train**, причём отдельно для входа FM и для расстояния retrieval? Если даже этот первый шаг нестабилен, не тратить десятки минут на FM-инференс и не выдавать oracle-абляцию за метод.

Сходные идеи не следует называть новой feature selection или metric learning: [MALTS](https://jmlr.org/papers/v23/21-0053.html) учит метрику по предсказанию outcome, а [CausalPFN](https://arxiv.org/html/2506.07918v2) применяет retrieval на больших таблицах. Здесь проверяем лишь разделение двух наборов признаков для конкретной causal FM.

## Дизайн

- Восемь независимых train-наборов по 8192 строк, seeds `211–218`. 32 непрерывных столбца: четыре прогностических `P`, четыре модификатора эффекта `M` и 24 независимых шумовых. Первые восемь латентных координат коррелируют как `0.25^|i−j|`, затем все 32 столбца случайно переставляются **отдельно для каждого seed**. `T~Bernoulli(0.5)`. `mu0=0.35P0+0.25sin(P1)+0.20P2+0.15(P3²−1)`, `tau=0.35tanh(M0+0.5M1)+0.15sin(M2)+0.10M3`, `Y=mu0+T*tau+Normal(0,0.4)`. Метод видит только `X,T,Y`; истинные индексы используются **после** ранжирования для диагностики. Eval-набор и FM-score в E06 не создаются.
- Для каждого seed стратифицированное разделение train 75/25 (seed `seed+6000`), затем два `HistGradientBoostingRegressor`, отдельно на control/treatment fit-строках. Фиксировано: `learning_rate=.05`, `max_iter=200`, `max_leaf_nodes=31`, `l2_regularization=1`, `random_state=42`, `OMP_NUM_THREADS=4`. Никакого подбора по результатам этого теста.
- На внутренней validation каждый столбец переставляется трижды фиксированным RNG (`seed+7000`). **Input importance** — среднее увеличение arm-specific MSE при перестановке в соответствующем предсказании `mu_t`; взвешивание по фактической численности arm. **Retrieval importance** — увеличение Robinson R-loss `(Y−m(X)−(T−0.5)tau(X))²` при перестановке столбца только в `tau_hat=mu1_hat−mu0_hat`, оставляя `m_hat=(mu0_hat+mu1_hat)/2` на исходных validation `X`. Это train-only proxy, не истинная CATE-importance. Отрицательные importance допустимы. При равенстве — меньший номер столбца.
- Зафиксировать top-8 по input importance для входа FM и top-4 по retrieval importance для поиска. Наборы могут пересекаться. Бюджеты 8 и 4 известны из дизайна synthetic и пока не являются правилом выбора числа признаков на неизвестном реальном датасете.

## Primary gate и решение

В каждом seed посчитать число настоящих `P∪M` в input top-8 и число настоящих `M` в retrieval top-4. **Продолжать к отдельному FM-эксперименту только если** минимум в 6/8 seeds input находит ≥6/8 и retrieval находит ≥3/4. Это описательный gate осуществимости, выбранный до результатов; он не проверяет PEHE или ценность политики. Средние hit counts, список выбранных столбцов и importance сохранить полностью. Если gate не выполнен, не менять thresholds/seeds и не запускать FM по этому варианту метода.

Если gate выполнен, следующий заранее обозначенный вопрос для **новой версии/эксперимента с новыми seeds и eval**: сравнить полный FM, выбранный input при том же retrieval, разделённые наборы input/retrieval, oracle ориентир, direct local и global T-Learner на одинаковых train/eval, с primary PEHE и secondary oracle regret@10%. E06 сам по себе не даёт права заявлять такой выигрыш.
