# CS04 / E01 / v001 — чувствительность feature-контекста к лишним признакам

- **Статус:** plan. Протокол записан после результатов CS01 и CS03, но до генерации новых данных и расчёта метрик. Это прицельная проверка механизма, выбранная по старым наблюдениям.
- **Вопрос:** если добавить к тем же объектам нерелевантные признаки, портит ли поиск соседей по ним точность CausalPFN при неизменном входе модели?
- **DGP:** воспроизвести `three_groups_v1` из [CS03/E01](../../../CS03/experiments/E01/v001.md): первые 8 признаков `Uniform[-1,1]`, treatment `Bernoulli(0.5)` независимо от признаков, те же формулы `p0`, `tau`, `p1=p0+tau`, outcome `Bernoulli(pT)`. В варианте `d32` добавить 24 независимых `Uniform[-1,1]` признака, которые не входят в `p0`, `tau` и treatment assignment. Для одного generated seed варианты `d8` и `d32` используют **ровно те же** первые 8 признаков, treatment, outcomes и истинный CATE; меняются только дополнительные столбцы. Новые generated seeds `61–70`, по 8192 train и 2048 eval строк. Потоки RNG для базовых данных и дополнительных признаков разделить через `SeedSequence`.
- **Одинаковый ресурс:** закреплённая CausalPFN revision `83aad07da1cb077cfda4236878a1b07dc9f72a54`, CPU, `K=512`, 256 control и 256 treated train-строк для каждого eval-запроса. Признаки стандартизовать только по train. На одних train/eval IDs посчитать пять конфигураций: модель с 8 признаками + `random_query_s981` или feature-kNN по 8; модель с 32 признаками + тот же random, feature-kNN по **первым 8** или feature-kNN по **всем 32**. Варианты поиска по 8 и 32 при входе модели из 32 признаков используют один и тот же model input и labels; отличается только контекст. Случайный контекст имеет те же train-индексы в обеих размерностях. Новых labels, weak learners или подбора параметров нет. Query-dependent random исправляет отличие старой синтетики CS03, где random-контекст был общим для всех запросов.
- **Primary:** `cate_rmse = sqrt(mean((score − true_CATE)^2))`; меньше лучше. Для каждого generated seed определить `P = RMSE(model32, feature32) − RMSE(model32, feature8)`. Положительный `P` означает, что нерелевантные признаки **в поиске соседей** ухудшили CATE RMSE при неизменном входе FM. Первичный описательный ориентир: средняя `P > 0` и минимум 8/10 seeds с `P > 0`. Также нужно исходное преимущество feature8 над random при `model8`: `B8 = RMSE(model8, random) − RMSE(model8, feature8)`, среднее `B8 > 0`; иначе исследуемый выигрыш изначально отсутствует.
- **Secondary:** `B32 = RMSE(model32, random) − RMSE(model32, feature32)` и полное изменение преимущества `A = B8 − B32` смешивают влияние поиска и размерности входа модели, поэтому это только дополнительные контрасты. Показать Q̂ (`normalized_qini_auc`) на тех же observed eval исходах, истинный policy regret@10%, CATE-neighbor MAE, средние эффекты по seeds и runtime. Q̂ и regret не заменяют primary после просмотра результатов. Истинный CATE используется **только** для оценки и диагностики соседей, не для выбора контекста.
- **Неопределённость:** 10 generated datasets являются единицами повтора. Показать все 10 парных `P`, их среднее, число положительных, 95% percentile bootstrap-интервал среднего по 10 seeds (10 000 resamples, seed `982`) и точный двусторонний sign-test как дополнительную диагностику. Интервал по eval-строкам не выдавать за независимые DGP-повторы. Иных сравнений не делать primary.
- **Хранение:** полные generated data, scores и context IDs — в `artifacts/local/cs04_e01_results/`, компактный неизменяемый снимок с протоколом, всеми seed-level метриками, SHA данных/кода и статусом — в `results/E01/v001/<run-id>/`. При прерывании сохранить `incomplete`; seeds не заменять.

Перед полным запуском проверить pinned checkpoint, `--help`, генерацию парных `d8/d32` без просмотра метрик, treatment balance/отсутствие дублей в контексте и небольшой smoke-инференс. Полный запуск и вывод оформлять после фиксации кода и протокола в Git.
